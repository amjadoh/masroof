# Beta settings, saved state and local restore recovery

This slice adds an actual **Beta settings** route (M10.3/M10.4) and strengthens
the existing local Beta snapshot flow (M11). It is not production migration
acceptance or a claim that M10/M11 are complete. The subsequent
[encrypted recovery increment](M11_ENCRYPTED_RECOVERY.md) adds user-selected
SAF documents restricted to this trusted Beta installation.

## UI and state

The route exposes persisted system/light/dark appearance, local snapshot status,
backup, restore and Beta reset. Restore/reset require explicit confirmation;
Cancel/Back never writes. Confirmation and route state survive saved-state
recreation. The actual Activity applies the persisted appearance, and the
existing saveable shell scroll state remains in use. A running maintenance
operation blocks close/return and duplicate actions. UI effects run on the same
Beta FIFO executor as container lifetime work, so recreation cannot open another
Room instance ahead of the preceding close/write.

Old direct maintenance buttons remain compatible for existing isolated component
callers, but the actual Beta Activity hides them: real restore/reset can only be
invoked through the confirmed settings flow. Startup recovery/validation failure
shows Retry/Return and preserves the original files; it does not reset or create
replacement financial data.

## Snapshot boundary

Only `masroof_beta.db` and `masroof_beta_prefs` are involved. Snapshots live in
the app-private `beta_recovery_v1` folder. Each immutable generation contains the
SQLite file, JSON string preferences (newlines and equals signs round trip), and
a manifest bound to BETA, the fixed database identity, supported schema version
and SHA-256 of both payload files. An AtomicFile pointer publishes a fully
validated generation. Failure while making a new generation leaves the previous
published snapshot available.

Before its manifest is sealed, a new isolated snapshot is checkpointed into
DELETE journal mode. Published snapshots are inspected through read-only SQLite
connections, so native Android cannot create WAL/SHM entries inside an immutable
generation. Staged Room migration uses TRUNCATE mode, leaving a standalone
database for installation. A native-device regression checks exact archive
entries before/after read-only inspection and restore; external force-stop
journeys repeat the entry and preference checks after reopening.

**The private snapshot format alone uses corruption checks, not authentication.**
The subsequent encrypted-document flow authenticates its complete payload and
requires the existing installation origin key before using this restore path.
No production backup reader is exposed. Old unsealed database/text pairs are not automatically trusted
or installed. The historical v5 migration fixture explicitly packages its
synthetic database through the new internal writer to retain migration coverage.

## Restore and interruption

Restore copies into an isolated staging folder, validates checksums, strict
metadata shape, SQLite integrity and foreign keys, and opens the staged copy
through current Room migrations. It compares the complete table set and Room
TableInfo (columns, defaults, primary keys, foreign keys and indices) with a fresh
database generated by the current Room implementation. A matching Room identity
hash alone is insufficient. Versions newer than `BetaDatabase.VERSION` fail
closed; older supported versions migrate only in staging. There is no fixed
table allowlist: the separately coordinated 7→8 additive schema is preserved by
the same current-schema capability after integration.

Before replacement, the original database **and any WAL/SHM/rollback journal**,
plus original preferences, are retained with checksums. A durable REPLACING
journal precedes the first live write. Startup recovery runs before Room opens:
an uncommitted operation restores the original generation; a COMMITTED journal
keeps the restored generation. Rollback uses atomic moves of retained originals,
without requiring another full database copy on a low-storage device. If rollback
itself is killed between moves, hashes identify already moved originals at their
destination and recovery resumes. Missing/corrupt recovery originals fail closed
with files preserved for recovery.

An abrupt stop before the journal is published can leave an unreferenced private
staging directory. It cannot become the active database. Automatic startup pruning
is deferred; explicit confirmed Beta reset erases these validated stage directories
as well as published generations. Metadata deletion is verified before deleting
recovery originals, so an I/O failure cannot leave a journal pointing to discarded
rollback material.
Confirmed reset also checks deletion of the exact Beta installation temporary file,
the existing flat Beta backups, the live Beta database and Beta preferences; a
reported deletion/commit failure cannot be shown as successful reset. Reset is an
explicit destructive operation, not a transaction that promises rollback of an
already erased database after subsequent preference/storage failure.

The live database is closed before container maintenance. Offline restore callers
must likewise have no open database handles; the actual Activity serializes all
such work. Storage errors before cutover leave the live database untouched;
errors after cutover attempt journal rollback and otherwise retain the journal
for startup retry. Full disk or broken storage can still prevent recovery from
finishing: this is an explicit unavailable state, never success or an empty
financial dashboard.

## Verification

JVM cases exercise JSON preference fidelity, corrupt DB/preferences/manifest,
failed backup publication, interruption before/after database and preference
installation, commit-before-cleanup, malformed recovery journal, and missing
table with unchanged identity hash. Android settings interaction cases exercise
saved confirmation/cancel, persisted theme and actual confirmed backup/restore
with corruption handling. The existing API 36 lifecycle job gains real UID
force-stop journeys at database installation, preferences installation and commit,
plus a two-kill journey preserving a committed WAL-only row across offline
restore interruption. No additional emulator job/matrix is introduced.

No production databases/preferences are read by these implementations. Tests use
synthetic isolated state. No old production code is deleted. Remaining M11 work
includes cross-device/key-recovery acceptance for encrypted copies, broader
transfer/production migration acceptance and performance/large-dataset qualification. Broader M10
language/notification/configuration and full screen-state parity remain open.
